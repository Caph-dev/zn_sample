# 自动审批独立子页面与自定义审核方案实施计划

日期：2026-09-08  
状态：已实施（P0–P3 代码与离线验证完成，见分支 `auto-approval-page`）；本文件不构成执行真实批准、写飞书或发送私信的授权。实店全链路验收须另获明确授权并默认限量 1。

## 1. 目标与边界

新增独立「自动审批」子页面，让业务员通过按钮、checkbox、数字输入框配置本次审核标准，完成：

配置规则 → 只读筛查 → 查看名单及证据 → 明确确认 → 限量批准 → 可选填表 → 核对及补写。

典型需求：仅选择 B005，仅启用履约率/预计发布率 >85%，不检查其余销售指标及内容审查，按本次自定义标准审批并写表。

- 保留正式 SOP、默认阈值及原有 0/1/2/3 入口行为，不把临时标准变成全局默认。
- 自定义规则仅绑定本次任务；关闭检查不等于检查通过。
- 允许大幅调整当前页面的布局、导航及交互，但不能破坏物流、跟进、任务、报表、诊断和既有操作入口。
- 不实现定时审批、多店并行、自动拒绝、任意表达式、运行中改规则或自动私信。
- 不提供撤销平台审批的假象，不给正在执行写操作的任务提供取消按钮。

## 2. 已核实的现状

- `assistant/web/templates/base.html` 使用服务端模板、HTMX、原生 JavaScript，以及静态主题 CSS；不是现成的 React 组件页面。
- `assistant/web/static/app.js` 和 `app.css` 承载既有网页交互与样式。

- 有 Astryx 主题不代表已经复用了 Astryx React components，不能只给原生表单换 CSS 就算完成接入。
- `assistant/jobs/handlers/operator.py` 只映射四个固定 operator 模式；不得把它改造成网页任意参数/命令执行器。
- `assistant/api/jobs.py` 已有持久任务与可恢复 SSE，优先复用任务、进度和互斥设施。

## 3. Astryx 接入要求与安装步骤

官方依据：https://astryx.atmeta.com/docs/working-with-ai 。本次已通过安装在项目中的 `npx astryx docs working-with-ai` 读取对应 CLI 文档；实施时再次核对在线文档和实际安装版本。

### 3.1 安装与上下文初始化

由实施 Agent 自行完成安装，不要求业务员手工安装依赖。

1. 核对 package.json、锁文件、Node 版本及现有修改。选择兼容的 React/React DOM、TypeScript 和构建工具；先确认 core 的 peerDependencies，不猜版本。
2. 在现有 npm 工程上通过包管理器安装缺少的依赖；已有 Astryx 无需为了安装而重装或无关升级。依赖和锁文件必须一起提交。
3. 全新环境按锁文件安装；开发补依赖使用 npm install。不要修改系统或启动器 PATH。
4. 按官方执行 agent 上下文初始化：`npx astryx init --features agents`。先检查生成目标，保护 AGENTS.md 中业务纪律，仅更新 Astryx 管理块；不擅自安装影响其他仓库的全局 User Rule。
5. 读取生成的上下文；升级 Astryx 时重新生成，并按项目规则执行 `npx astryx upgrade --apply`，审核生成差异。
6. 入口导入 `@astryxdesign/core/reset.css` 与 `@astryxdesign/core/astryx.css`，按当前版本文档接入现有 Geist 主题。确认主题 CSS 与 core 版本兼容。

### 3.2 必须先发现组件，再写 UI

依次使用当前版本的 CLI：

- `npx astryx build "审批规则配置、只读筛查预览、确认执行的后台工作台"`
- `npx astryx docs layout`
- `npx astryx template --list`，选择相关模板，再读对应 skeleton。
- `npx astryx docs tokens`
- `npx astryx component <Name>`，核实实际使用组件的导入路径、props、可访问性和示例。

模板是参考，不机械复制整页。优先复用 Astryx 的页面框架、导航、表单、按钮、勾选、数字输入、选择器、列表/表格、提示及对话框；组件名必须通过 CLI 查询，不虚构 NumberInput 等名称或 props。

布局使用库组件，不手写 div/span 布局；样式优先组件 props，其次设计 tokens。禁止裸 hex/px、渐变装饰、Tailwind 工具类及新的随意颜色覆盖。数据用行和表格，不把每条规则/达人包装成嵌套 Card；状态用 StatusDot/Token，Badge 仅作数量。

## 4. 前端架构与页面设计

### 4.1 接入策略

建议新增 `/auto-approval`，由现有 FastAPI 返回独立 React 页面壳，构建产物由现有服务提供，不要求业务员额外启动 Node 开发服务器。

- 拟新增 `frontend/` 存放 React/TypeScript 源码，纳入根 npm 工作流；具体目录在实施时确认。
- 初期独立文档壳隔离 reset 和旧 app.css，防止全局样式污染 HTMX 页面。
- 两套页面共享导航语义、店铺提示和任务反馈体验；优先抽取可复用的 React 业务组件，而不是为每个页面重造按钮。
- 允许重做工作台/导航，但采用渐进迁移，不以本任务为由重写全部业务页面。
- 构建产物目录建议 `assistant/web/static/auto-approval/`；生产与 Windows/macOS 启动/打包流程必须先构建或随发行包分发产物。
- 不覆盖现有手工维护静态资源、字体和主题文件，不产生与现有 build:theme/build:fonts 冲突的构建路径。

### 4.2 信息架构

主导航新增「自动审批」。桌面采用主规则区 + 次要摘要区，窄屏纵向排列；关键确认按钮不遮挡内容。满足键盘操作、可见焦点、输入标签、错误关联和非颜色状态提示。

页面分四区：

1. 运行准备：店铺名称/ID、短超时 execute_script 探活、登录/页面状态、冲突任务、检查环境按钮。不因 running 有店就显示就绪；busy 时复用既有缓存，不并发探测。
2. 规则配置：标准 SOP/自定义按钮，分组条件行，实时中文摘要。
3. 只读结果：统计、名单、指标值、证据来源、失败/待复核原因、可批准名单选择。
4. 执行确认：店铺、规则、名单、限量、填表开关、自定义规则例外确认、输入 `y` 后执行。

### 4.3 规则控件与语义

模式：标准 SOP 只读；「复制为自定义」创建独立草稿，不修改正式默认值。首次进入默认标准模式，自定义选择不能静默跨任务复用。

商品：从验证过的主推款中多选，默认 B005，至少一款。显示货号和名称，保存商品 ID；不开放任意 ID 或「跳过主推校验」。

基础条件可勾选启用，数字初值沿用正式 SOP：

- 粉丝数 >2000。
- GMV >1500 USD。
- 成交件数 >80。
- 千次曝光成交/GPM >10。
- 客单价 10–25 USD，包含上下限。
- 履约率/预计发布率 >80%。
- 女性粉丝占比 >60%。
- 类目命中勾选集合中任一项，初始为既有七类白名单。

第一版固定比较运算符，开放开关和阈值，不做任意逻辑树。基础条件之间为 AND。数字校验由前后端共同执行：有限数值、非负、计数整数、百分比 0–100、上下限合法；启用值不得为空。不允许仅选商品、所有审核项关闭后自动批准。

视频/直播为高级组：视频 GPM >10、均播 >300、互动 >2%；直播 GPM >12、平均观看量 >1000。支持指标启用与数字调整，启用组至少包含一项；同时启用两组时可选「任一侧」或「两侧均满足」。组内为 AND，组间逻辑必须在摘要中显示。

内容组：启用开关、最近天数（默认 7）、相关视频数（默认至少 4）、是否要求至少一条明确展示。第一版采用合理的后端上限限制采集成本，具体上限在实现前结合采集能力确定，前端不得无限输入。相关类目沿用既有七类，与销售类目选择不暗中联动。展示定义仍为穿在身上，或同画面露脸并手持产品，不新增强制 ASR/每日配额。

关闭内容审查时显示醒目风险说明和「未执行」，不生成虚假内容证据。启用时完整不足计数为失败，部分采集证据不足为待复核，足够的已知下界加展示证据可短路通过。

### 4.4 指标缺失和来源

- 自定义模式中，启用指标缺失不得默认通过；不启用则记 not_checked。
- 已知违反任一必需条件为 failed；无已知失败但必要证据不足为 needs_review；完整满足才为 passed。
- OR 组一侧通过即可；两侧均失败才失败，其余未决组合待复核。AND 组已知失败即失败，否则有未决即待复核。
- 正式 SOP 保持原有缺失值语义，包括部分均播/互动缺失不单独否决，不能因新页面上线悄悄改变。
- 履约指标保持既有详情预计发布率优先、否则列表履约率的口径；每行显示来源和采集时间。不要为了仅检查该指标强制拉取全部详情。
- 列表 GPM 近似值必须标记为近似，详情官方值优先；预览和批准验证使用一致口径，不静默切换。

### 4.5 预览与确认

- 主动作先是「开始只读筛查」。结果分为符合、不符合、待复核、执行拦截；只有符合且无安全拦截的行可选。
- 可取消候选，不允许勾选失败行强批；空名单禁用执行。
- 修改商品、条件或阈值立即使旧结果失效，要求重新筛查。
- 限量默认 1，零/负值不能变为不限；超过上限时显示实际执行行和顺序。
- 写飞书默认关闭；确认文本列明目标为「达人关系管理(新) / 达人管理总表」。
- 自定义模式额外确认「本次按自定义标准，不代表完整 SOP 通过」。确认框不是身份认证或主管授权；权限能力须以现有系统实际认证机制为准。
- 任务状态通过既有事件/SSE 展示，刷新可恢复。网络异常先查任务状态，不再次创建批准任务。

## 5. 后端规则、存储与 API

### 5.1 规则模型与策略隔离

拟新增领域模型/服务，不通过把 Criteria 阈值设为 0/负无穷来假装关闭检查。

规则包含 schema_version、mode、product_ids、启用条件与数值、视频/直播组逻辑、内容参数、指标来源策略。采用严格 schema：拒绝未知字段、非有限数字、非法范围、空条件组合与非允许商品。

标准策略调用原有规则和内容校验。自定义策略独立计算各项结果并生成「自定义通过证据」，不能赋予伪造的 sales_eligible/content_review_status。

必须明确改造批准边界：按可信任务的策略类型分派验证。正式入口与旧导出继续严格走原 `_guard_content_review()`；自定义入口只接受服务器生成的自定义快照及逐项证据。缺策略、版本未知或未执行必需检查均拒绝。禁止前端传一个跳过内容校验的布尔量直接关闭门禁。

### 5.2 持久化

通过数据库迁移保存：

- 规则快照：规范化内容、版本、服务端计算的摘要/hash、创建时间。
- 筛查批次：店铺、规则引用、采集范围与完整性、开始/结束时间、状态。
- 候选：申请 ID、达人 ID、商品 ID、原始指标引用、来源、逐项结果、总体结论、安全拦截。
- 执行批次：筛查批次、选中行、确定顺序、限量、填表开关、确认记录、幂等键、任务 ID。
- 执行明细：批准与飞书分别记录状态、错误、证据、重试/补写关系。

hash 仅用于一致性，不作为授权。授权依据为服务器保存的任务、绑定店铺/申请和实际校验。不要让客户端任意指定本地导出路径或 JSON 文件充当可信快照。

### 5.3 API 草案（实施时对齐现有认证/CSRF）

- GET `/api/auto-approval/options`：允许的条件、范围、默认值和主推商品。
- POST `/api/auto-approval/previews`：提交结构化规则，校验后创建只读任务。
- GET `/api/auto-approval/previews/{preview_id}`：规则快照、结果分页、完整性和状态。
- POST `/api/auto-approval/executions`：提交 preview_id、候选 ID、限量、填表选择、明确确认和幂等键；不接收任意规则覆盖或命令。
- GET `/api/auto-approval/executions/{execution_id}`：批准/写表分项结果，事件复用现有任务 SSE。
- POST `/api/auto-approval/executions/{execution_id}/reconcile`：核对未知结果、延迟确认和受限补写，不重新批准。

状态建议：草稿 → 筛查中 → 可确认/无候选/失败；执行批次另为已确认 → 执行中 → 完成/部分完成/待核对/失败。页面本地改规则后旧预览不可执行，后端同时验证规则引用和版本。

## 6. 执行、安全与异常处理

- 新增白名单任务 handler，与现有队列、店铺/Bridge 互斥、进度及脱敏日志集成；不能只添加 handler 而漏掉锁和禁止取消策略。
- 不修改四个旧 operator 模式的参数契约；新增明确的专用入口，继续通过现有 `--execute --yes` 门闩和同一 execute-limit 预算。
- 固定 sys.executable 和允许的 argv；不执行网页 shell 字符串，不提供任意脚本/路径/环境变量输入。子进程保持 UTF-8。
- 复用已验证的批准传输、去重、主推映射、备份及飞书写入服务；不猜 endpoint，不绕过现有安全门闩另写裸 API 请求。
- 真正执行前再次核对店铺、申请身份、待审核状态、主推映射、去重、规则证据和新鲜度。新鲜度期限作为后端固定策略，在实施时确定；超期要求重新筛查。
- 若复查出现影响规则的变化，跳过该行并说明，不能更换口径后仍盲批。
- 重复点击、HTTP 重试、服务重启不得重复批准；批准调用前持久化意图，响应未知进入待核对，不自动重放。
- 平台 success_count=1 视为批准成功，不等待发货；列表约 10 分钟延迟通过既有 confirm 流程处理。
- 写表失败仅补写；批准结果未知不先写。记录「批准成功但填表失败」，不能整体失败后重批。
- 飞书新建默认人员=王良希（技术）、合作状态=待发货、是否已寄样=否。不得写旧表或主推表。
- confirm 回填订单号只接受有效 15–20 位非零 main_order_id，不覆盖不同已有订单号；补写/回填共享既有执行限量。
- 不发送介绍或物流私信，不自动切店、不重开店。导航继续遵守已登录起点和 --from-seller-home 契约。
- 实现涉及自动化前按 AGENTS.md 完成 doctor、execute_script 和店铺确认；验证默认只读，不以完成开发为由执行真实写入。

## 8. 实施分期

### P0：规则与基础接入

明确自定义审批例外边界、数值上限、指标口径、新鲜度；安装缺失前端依赖；验证 Astryx 组件和构建路线；更新 gitignore。同步更新 AGENTS.md 中「网页不能自定义参数」及「批准必须内容审核」的描述，仅增加隔离例外，不删除正式规则。业务说明同步 README，配机变化只写快速开始。

### P1：只读端到端

新增路由、React 页面、规则 schema、快照存储、预览任务、规则摘要及结果列表。只做真实只读采集，批准按钮保持不可执行，证明不同条件按需采集，不无条件跑完整详情/视频。

策略分派、批准边界验证、幂等和互斥、确认、限量、备份、写表及核对补写。保留旧链路回归。不得通过旧 operator_pipeline 实现本页执行，因为它还包含私信动作。

### P3：页面与交付验收

桌面/窄屏、键盘、错误提示、SSE 断线恢复、旧页面兼容；构建与发行验证；重启操作台使新代码生效；更新文档。真实平台验收另获明确授权并默认限量 1。

## 9. 有价值的验证与验收标准

- 规则单元测试：85 整不通过，85 以上通过；空值待复核；关闭指标 not_checked；非法数值拒绝；客单价边界；视频/直播 AND/OR 三态逻辑。
- 策略隔离：标准 SOP 结果不变；无内容证据的旧导出仍拒绝；自定义关闭内容可按合法自定义证据通过，但不能被冒充为标准通过。
- API 安全：篡改候选/店铺/版本/规则、未知字段、重复执行、超限、未确认、CSRF 不合法都拒绝；hash 相同不自动获得授权。
- 副作用模拟：批准成功后写表；批准未知不写表不重批；填表失败只补写；重启恢复；店铺锁冲突；执行中取消被拒绝。
- 前端：数字和开关可键盘操作；摘要准确；修改规则使旧结果失效；只允许合格行选择；明确实际执行数量；平台与飞书状态分开显示。
- 构建：类型检查、构建、编辑文件 ReadLints、重点测试通过；无新引入的全局样式回归；新电脑按文档可构建运行。
- 典型业务验收：B005 + 仅发布率 >85% 的只读名单与手工核对一致，其他未启用项不影响自定义结果；在模拟写入环境完成确认、限量和填表链路。
- 全过程不得把模拟通过描述为真实实店验收；实际批准、飞书写入及私信默认不执行。

## 10. 完成定义

业务员不编辑脚本即可配置规则；每条通过都有可追溯证据；临时方案不改变正式默认；前端真实复用 Astryx components；执行继续受确认、限量、去重、备份及结果核对保护。页面可大改，安全边界不能被 UI 简化掉。
