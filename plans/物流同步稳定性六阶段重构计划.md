## 总体目标

将当前流程：

```text
读取 tab 30/40
→ 每一行进入订单页
→ 查询一个订单
→ 返回样品申请页
→ 下一行重复
```

改造为：

```text
一次读取 tab 30/40
→ 合并、去重并建立订单查询计划
→ 根据本地状态筛出本轮确实需要刷新的订单
→ 一次进入商家订单页并确认页面稳定
→ 在同一订单页依次执行现有白名单物流 GET
→ 按订单结果更新关联的所有样品记录
→ 一次返回样品申请页
```

这里的“批量查询”仅表示：**一次进入订单页，在同一页面上下文中对多个唯一订单依次调用现有、已验证的物流 GET。**

不猜测 TikTok 是否支持一次 HTTP 请求传多个 `main_order_id`，不扩大 API 白名单，不增加任意命令或参数入口，也不改变任何写操作门闩。

## 阶段一：消除逐单跨域往返

### 目标

将导航和单订单查询解耦。整个同步批次只执行：

- 一次样品申请页 → 商家订单页；
- 一次商家订单页 → 样品申请页。

无论批次中有多少订单，都不再逐单往返。

### 当前问题

`ShipmentService.synchronize_shipments()` 当前在循环内调用 `fetch_tiktok_logistics_details_api()`。该函数同时负责导航、读取 seller page context、查询一个订单及解析详情。服务层又在每行的 `finally` 中返回样品申请页，导致每个订单都触发完整跨域往返。

### 实施方案

#### 1. 拆分订单 API 职责

在 `scripts/lib/order_api.py` 中保留现有单订单公开函数以兼容其他脚本，同时增加内部层次：

```python
def enter_seller_order_page(...) -> SellerPageContext:
    """进入订单页、确认稳定，并返回可复用的页面上下文。"""


def fetch_logistics_payload_in_seller_context(
    store_id: str,
    order_id: str,
    *,
    context: SellerPageContext,
    fulfill_unit_ids: Iterable[str] = (),
) -> dict[str, Any]:
    """假定已经位于订单页，只执行当前订单的白名单物流 GET。"""


def fetch_logistics_details_in_seller_context(...) -> dict[str, Any]:
    """在现有 seller context 中查询并解析一个订单。"""
```

现有 `fetch_tiktok_logistics_details_api()` 改为兼容包装，继续支持“进入订单页 → 查询一个订单 → 返回详情”，使第 3 号旧脚本等调用方不必同时迁移。

#### 2. 服务层改为批次控制

`ShipmentService.synchronize_shipments()` 调整为：

```text
读取 tab 30/40
→ 建立订单查询计划
→ 持久化没有合法订单号的样品记录
→ 如果存在待查订单：
    进入订单页一次
    读取 seller context 一次
    逐个查询唯一订单
    逐个隔离失败
→ finally 返回样品申请页一次
```

#### 3. 单订单失败不终止整个查询批次

每个订单独立捕获只读查询异常：

```text
订单 A 超时 → 记录 A 失败 → 继续查询 B
订单 B 成功 → 正常持久化
订单 C schema 错误 → 记录 C 失败 → 继续查询 D
```

仅以下批次级错误停止后续查询：

- 无法进入商家订单页；
- 页面稳定契约失败；
- seller context 无法建立；
- Bridge 已不可用；
- 返回样品申请页失败；
- 用户在安全检查点取消任务；
- 整体 deadline 已到。

#### 4. 页面返回规则

使用最外层 `try/finally`：

```python
entered_seller_order_page = False

try:
    ...
finally:
    if entered_seller_order_page:
        navigate_to_sample_request(...)
```

禁止继续在每个订单自己的 `finally` 中导航。

### 主要修改文件

- `assistant/services/shipment_service.py`
- `scripts/lib/order_api.py`
- `scripts/lib/sample_navigation.py`
- `tests/assistant/test_shipment_sync.py`
- `tests/test_order_api.py`

### 测试与验收

构造订单 A 成功、订单 B 查询失败、订单 C 成功、非法订单 D 的场景，断言：

- 进入商家订单页仅一次；
- seller context 只读取一次；
- 物流 GET 只对 A/B/C 调用；
- B 失败不阻止 C；
- D 不产生 GET；
- 返回样品申请页仅一次；
- 返回失败时任务报告批次级错误。

对于 100 个唯一订单：跨域进入次数为 1，返回次数为 1，物流 GET 次数不超过 100。

## 阶段二：按 `main_order_id` 去重并合并履约单元

### 目标

在订单页导航之前，将 tab 30/40 的样品行整理为唯一订单查询计划：

```text
一个 main_order_id
→ 一次物流 GET
→ 一组关联样品行
→ 一组去重后的 fulfill_unit_ids
```

### 数据结构

建议在 `assistant/services/shipment_service.py` 中增加清晰的数据类：

```python
@dataclass
class ShipmentRowCandidate:
    row: dict[str, Any]
    source_status: int
    sample_case_id: int | None = None


@dataclass
class OrderQueryPlan:
    main_order_id: str
    fulfill_unit_ids: tuple[str, ...]
    candidates: list[ShipmentRowCandidate]
```

### 归一化规则

#### `main_order_id`

统一执行 `str(value).strip()`，只有满足现有规则 `^\d{15,20}$` 的订单进入远端查询。空字符串、`0`、非 15–20 位数字及其他非法值不请求订单接口。

#### `fulfill_unit_ids`

对同一订单的所有样品行：

1. 转为字符串；
2. 去除首尾空白；
3. 丢弃空值；
4. 按首次出现顺序去重；
5. 保持稳定顺序，便于生成一致的 request fingerprint。

例如：

```python
["unit-1", "unit-2"]
["unit-2", " unit-3 ", ""]
```

合并为：

```python
("unit-1", "unit-2", "unit-3")
```

#### 跨 Tab 状态

同一个样品申请同时出现在 `tab=30` 和 `tab=40` 时：

- 不重复查询订单；
- `SampleCase.curr_status` 保持单调，只能升级到 40，不能回退到 30；
- 同一 `SampleCase` 本轮只持久化一次物流结果；
- 同一个订单可以关联多个不同 `SampleCase`。

### 防御性清洗

即使服务层已经去重，`build_logistics_query()` 仍应防御性清洗空白、重复、`None` 和非字符串值，避免其他调用方绕过服务层时产生不一致 query。

### 主要修改文件

- `assistant/services/shipment_service.py`
- `scripts/lib/order_api.py`
- `tests/assistant/test_shipment_sync.py`
- `tests/test_order_api.py`

### 测试与验收

覆盖：

- 同一订单跨 tab 重复；
- 相同订单关联多个申请；
- 重叠的 fulfill IDs；
- 不同订单不得误合并；
- 同一案例本轮只生成一次 Snapshot。

任务结果增加：

```python

    "rows": 112,
    "unique_orders": 78,
    "duplicate_rows": 34,
}
```

并满足：

```text
物流 GET 次数 <= 唯一合法 main_order_id 数量
```

## 阶段三：增量同步与安全持久化

### 目标

不再每次刷新 tab 30/40 中的全部历史订单，只刷新确实需要更新的订单；同时确保临时 unknown 或接口错误不会清除已知物流事实。

### 增量判定原则

订单满足以下任一条件时进入本轮远端查询：

1. 本地尚无 Shipment；
2. 尚未确认 Delivered；
3. 没有有效 tracking number；
4. 当前状态为 `unknown`、`exception`、`lost` 或其他需复核状态；
5. 上一次同步失败；
6. `fulfill_unit_ids` 发生变化；
7. 距上一次成功同步超过刷新周期。

只有同时满足以下条件时才能直接跳过：

```text
已经 Delivered
且 delivered_at 非空
且不需要人工确认送达时间
且 tracking number 有效
且上次成功同步没有错误
且 fulfill_unit_ids 没有变化
```

### 建议刷新策略

使用代码常量而不是散落数字：

```python
ACTIVE_SHIPMENT_REFRESH_INTERVAL = timedelta(hours=6)
EXCEPTION_SHIPMENT_REFRESH_INTERVAL = timedelta(hours=1)
DELIVERED_SHIPMENT_REFRESH_INTERVAL = None
```

建议语义：

| 状态 | 刷新策略 |
|---|---|
| 无本地 Shipment | 立即查询 |
| unknown / 上次失败 | 每次任务尝试，或最短退避后尝试 |
| in_transit / out_for_delivery | 距上次成功同步超过 6 小时 |
| exception / lost / returned | 距上次成功同步超过 1 小时 |
| delivered 且时间、单号完整 | 默认永久跳过 |
| delivered 但缺时间或需人工确认 | 继续刷新 |
| delivered 但缺 tracking | 继续刷新 |

不新增网页或 CLI 参数绕过这些契约。

### 数据模型

为严格区分“最近尝试”和“最近成功”，建议新增迁移，为 `Shipment` 增加：

```text
last_attempted_at
last_successful_sync_at
request_fingerprint
last_error_at
```

字段语义：

- `last_attempted_at`：无论成功失败均更新；
- `last_successful_sync_at`：只有收到并解析可信响应后更新；
- `last_error`：最近错误的脱敏摘要；
- `last_error_at`：最近错误时间；
- `request_fingerprint`：订单号与规范化 fulfill IDs 的 hash。

新增 Alembic migration，例如 `0002_add_shipment_sync_metadata.py`，并同步模型与迁移测试。

### 请求指纹

使用 `main_order_id` 和稳定去重后的 `fulfill_unit_ids` 生成 SHA-256。指纹变化时，即使 TTL 未到，也必须重新查询。不保存包含敏感参数的完整 URL。

### 安全合并规则

将远端观察结果分为 `success`、`unknown`、`error`。

#### `error`

- 不清空 tracking number、carrier、Delivered 或历史事件；
- 更新 `last_attempted_at`、`last_error`、`last_error_at`；
- 不更新 `last_successful_sync_at`；
- 不新增伪装成正常物流状态的 Snapshot。

#### `unknown`

- 本地没有事实时可以落成 unknown；
- 本地已有可信状态时，不得用 unknown 覆盖 Delivered；
- 空 tracking 不得覆盖已有 tracking；
- 不得清空 Delivered 时间；
- 可以记录本次 unknown 观察。

#### `success`

- 更新业务事实；
- 已确认 `delivered_at` 不得被 stale 的 in-transit/unknown 清空；
- 空 tracking 不得覆盖已有有效 tracking；
- ETA 不得当作实际送达时间；
- carrier exception 是物流业务状态，不等于 API error。

### Snapshot 策略

仅在以下情况新增 Snapshot：

1. 规范化业务 fingerprint 变化；
2. 同步结果从 success 变为 error；
3. 错误类型变化；
4. error 恢复为 success；
5. 首次观察。

业务 fingerprint 至少包括：

```text
tracking_number
carrier
status_code
status_category
status_label
estimated_delivery_at
delivered_at
last_event_at
last_event_text
package_count
```

仅 `checked_at` 变化不应产生新 Snapshot。

### 主要修改文件

- `assistant/services/shipment_service.py`
- `assistant/database/models.py`
- `assistant/database/migrations/versions/0002_*.py`
- `tests/assistant/test_shipment_sync.py`
- `tests/assistant/test_migrations.py`

### 测试与验收

覆盖首次同步、立即重跑、TTL 到期、请求指纹变化、上次失败、完整 Delivered、Delivered 缺时间、unknown 不回退、空响应不清 tracking、无变化不增加 Snapshot。

任务结果至少返回：

```python

    "rows": 112,
    "unique_orders": 78,
    "fetched": 12,
    "skipped": 66,
    "failed": 2,
    "changed": 5,
    "synchronized_cases": 14,
}
```

## 阶段四：建立订单页稳定就绪契约

### 目标

不再把 URL 包含 `/order` 作为开始物流 GET 的唯一条件。只有订单页满足明确稳定条件后，才建立 seller context 并执行查询。

### 稳定探测内容

增加轻量只读 JavaScript，返回：

```json
{
  "href": "...",
  "ready_state": "complete",
  "has_document_element": true,
  "has_body": true,
  "has_app_root": true,
  "is_login_page": false,
  "is_error_page": false
}
```

订单页稳定契约：

1. host 命中已验证 seller host；
2. path 包含 `/order`；
3. 不是紫鸟 `error.html`；
4. 不是登录页；
5. `document.readyState` 至少为 `interactive`，优先要求 `complete`；
6. `document.documentElement` 和 `document.body` 存在；
7. 能找到商家中心基础应用根节点之一；
8. 连续两次探测成功；
9. 两次探测的 canonical href 和店铺上下文一致；
10. `get_seller_page_context()` 能成功读取。

### 不应过度等待

物流数据来自同源 API，不要求：

- 某个具体订单出现在表格中；
- 所有异步组件加载完成；
- 特定易变化 CSS 类存在；
- 页面动画完成。

只确认页面 runtime 稳定、seller 同源上下文可用并能可靠执行 JavaScript。

### 连续两次成功

建议实现：

```python
wait_for_seller_order_page_ready(
    store_id,
    *,
    deadline,
    required_stable_probes=2,
)
```

两次成功之间保留 300–500ms 的短间隔。任意失败都清空连续成功计数，并在 deadline 内继续探测；稳定前禁止发送物流 GET。

稳定后只读取一次 `SellerPageContext`，整个批次复用。若中途发现页面离开订单 host、request state 丢失、runtime 重建或 context 失效，应停止新查询并进入批次恢复。

## 阶段五：统一真实墙钟 Deadline

### 目标

所有导航、稳定探测、页面 API 轮询和 sleep 都服从真实的 `time.monotonic()` deadline，消除：

- 名义 30 秒实际等待远超 30 秒；
- probe 超时不计入总预算；
- 固定 sleep 跨过 deadline；
- deadline 已到仍启动新的长时间 subprocess。

### 核心工具

建议增加内部 helper：

```python
def remaining_seconds(deadline: float) -> float:
    return max(0.0, deadline - time.monotonic())


def sleep_until_next_probe(
    deadline: float,
    requested_interval: float,
) -> bool:
    remaining = remaining_seconds(deadline)
    if remaining <= 0:
        return False
    time.sleep(min(requested_interval, remaining))
    return True
```

### 导航 Deadline

`navigate_to_url()` 创建或接收绝对 deadline：

```python
deadline = time.monotonic() + timeout
```

之后初始 href 探测、异步导航调度、settle 等待、href 轮询和稳定探测全部使用剩余时间。

删除“execute_script 超时不计入等待预算”的现有语义。`TimeoutExpired` 已经消耗真实时间，必须计入总体 deadline。

### 单次 Probe Timeout

单次 probe 保持短超时，但裁剪为：

```python
probe_timeout = min(
    HREF_PROBE_TIMEOUT_SECONDS,
    remaining_seconds(deadline),
)
```

剩余时间不足以完成最小 probe 时，不再启动 subprocess。

### 页面 API Deadline

`_post_page_json()` 中必须保证：

```text
poll subprocess timeout <= 当前剩余 deadline
sleep <= 当前剩余 deadline
retry backoff <= 当前剩余 deadline
```

浏览器端 AbortController 保留，但 Python 外层不得超过总 deadline。

### 阶段与批次预算

建议区分：

```python
SELLER_NAVIGATION_TIMEOUT = 45
SELLER_PAGE_READY_TIMEOUT = 30
PER_ORDER_LOGISTICS_TIMEOUT = 70
RETURN_TO_SAMPLE_TIMEOUT = 30
```

## 阶段六：只读路径的 `TimeoutExpired` 有限退避与结构化日志

### 目标

对安全、幂等的只读探测和物流 GET 提供有限退避；批准、发信等写路径继续禁止在不确定状态下自动重试。同时将缺乏上下文的 `error_type=TimeoutExpired` 升级为可定位阶段的结构化信息。

### 安全边界

#### 可以启用 timeout retry

- `location.href` 探测；
- 页面 readiness 探测；
- seller context 读取；
- 物流详情 GET；
- 页面异步 GET 的状态轮询；
- 其他明确幂等的 DOM/API 读取。

#### 禁止自动 retry

- 同意样品申请；
- 飞书写入；
- 私信发送；
- 邀请；
- 任何无法确认是否已产生副作用的页面动作；
- `location.replace` 导航调度也不能盲目重放，应先探测当前页。

### API 设计

不能让现有 `retries` 自动对所有 `TimeoutExpired` 生效。建议增加明确策略：

```python
class ExecuteRetryMode(Enum):
    NETWORK_ONLY = "network-only"
    READ_TIMEOUT_SAFE = "read-timeout-safe"
    NONE = "none"
```

也可使用显式布尔参数：

```python
zclaw_exec(
    ...,
    retries=2,
    retry_timeout_expired=True,
)
```

但默认必须是 `False`，只有只读调用点显式开启。

### 退避策略

建议：

- 只读探测最多 3 次总尝试，退避 0.5s、1.0s；
- 物流 GET 页面控制调用最多 2 次总尝试，退避 0.8s；
- 所有重试必须服从阶段 deadline；
- 剩余时间不足时不再重试。

### 导航调度的特殊处理

`schedule_page_navigation()` 超时不能直接重放，因为第一次调用可能已经成功安排了 `location.replace`。正确恢复流程：

```text
调度调用 TimeoutExpired
→ 不立即重复调度
→ 先执行短 href probe
→ 已到目标页则视为成功
→ 仍在原页且 deadline 足够时，再决定是否重新调度
```

## 阶段依赖与交付顺序

每一阶段应独立完成、测试和验收后再进入下一阶段：

```text
阶段一：一次进入订单页
  ↓
阶段二：订单去重与 fulfill ID 合并
  ↓
阶段三：增量筛选与安全持久化
  ↓
阶段四：订单页稳定契约
  ↓
阶段五：真实 deadline
  ↓
阶段六：只读 TimeoutExpired 退避与结构化日志
```

每个阶段都必须保持：

- 当前同步任务只读；
- 不写飞书；
- 不发送私信；
- 不改变第 3 号脚本的写操作门闩；
- 不猜测新 TikTok endpoint；
- 不把多个订单塞进未经验证的单次 HTTP 请求；
- 不增加网页可覆盖 store、limit、source 或 timeout 的参数；
- 任一阶段完成后现有测试继续通过。
