# 自动审批候选筛选流程（L0–L5）

> 适用页面：`/auto-approval` · 最后核对：2026-10-03（安全预筛、本轮 API 详情复用与视觉候选回看）
>
> 纪律与门闩总则见 [AGENTS.md](../../AGENTS.md)「自动审批子页面」。本文只回答一个问题：**一行待审核申请，经过哪些层才可能成为可批准候选**。不重复 SOP 原文，不构成执行授权。

## 0. 范围与非目标

**范围**：从待审核列表读取，到批准前逐行复算的完整筛选链路，含每层的证据、失败语义与代码锚点。

**非目标**：

- 不改变正式 SOP 入口（0/1/2/3）的判定与 `filters.Criteria`；
- 不描述跟进 / 物流 / 私信链路；
- 本文描述的是「筛选」；写操作门闩见第 3 节 L5 与第 7 节不变量。

## 1. 一句话概览

页面只负责「生成本次规则 + 展示结果 + 选择与确认」；**一行是否可批准，由服务端与脚本按同一套规则独立计算两次**：第一次在预览（生成候选名单与证据），第二次在批准前逐行复算并叠加平台预检。

## 2. 漏斗总览

漏斗共 6 层，编号 L0–L5：

```text
待审核 tab 全量行
  │
  ├─ L0 读取 + 数值抽取（全量，无业务筛选）
  ├─ L1 安全预检查 → 剩余目标按达人复用详情（仅视频/直播组启用时）
  ├─ L2 自定义规则三态判定（基础条件 AND + 视频/直播组）
  ├─ L3 安全拦截 blocked（主推 / 本次商品 / ID 完整 / can_be_approved）
  ├─ L4 内容审查（仅对 L2 通过且 L3 无拦截的行）
  └─ L5 执行边界复算（服务端候选子集 + 脚本逐行证据复算 + 4 道 preflight）
        → 窄 API 批准（限额内）
```

层号与代码的对应关系：

| 层 | 名称 | 主要实现 |
|---|---|---|
| L0 | 读取与数值抽取 | `load_pending_rows`（`scripts/lib/sample_data_source.py:166`）、`enrich_row`（`scripts/lib/filters.py:154`） |
| L1 | 安全预检查与按需详情复用 | `evaluate_custom_precheck`、`_enrich_preview_details` |
| L2 | 规则三态判定 | `evaluate_custom_row`（`scripts/lib/auto_approval_rules.py:498`） |
| L3 | 安全拦截 | `evaluate_custom_row` 尾段；`match_hero` / `reject_if_not_active_hero_product`（`scripts/lib/filters.py:75`） |
| L4 | 内容审查 | `review_creator_rows`（`scripts/lib/creator_video_review.py:721`）、`validate_content_review`（同文件 `:647`） |
| L5 | 执行边界复算 | `create_execution`（`assistant/services/auto_approval_service.py:422`）、`verify_row_evidence`（`scripts/lib/auto_approval_rules.py:882`）、`_run_execute`（`scripts/auto_approval.py:446`） |

## 3. 逐层定义

### L0 读取与数值抽取（无业务筛选）

| 项目 | 说明 |
|---|---|
| 输入 | 待审核 tab（列表全量行，分页上限由任务 argv 固定为 `--max-pages 50`） |
| 数据源 | `auto`（API 优先，失败回退 DOM）；来源会写入预览日志与信封 |
| 输出 | 原始行 + 抽取后的 `*_n` 数值字段 |

`enrich_row` 只做数值抽取与归一化，不做任何阈值判断；取不到的字段保持 `None`——启用项出现 `None` 即判 `failed`（详情采集失败除外，见 L2）。

| 字段 | 来源 | 说明 |
|---|---|---|
| `followers_n` | 列表 `follower_num` | — |
| `gmv_n` | 列表 `gmv` / `cell_gmv` | — |
| `units_n` | 列表 `item_sold` / `cell_units` | — |
| `views_n` | 列表 `content_video_views` / `cell_video_views` | 仅用于推导 GPM 近似值 |
| `fulfillment_n` | 列表 `fulfillment_rate` / `cell_fulfill` | — |
| `female_pct` | 列表 `top_follower_gender` | 列表只返回单一性别时按 `1 − male` 推导；未知性别键返回 `None`（待复核） |
| `categories_n` | 列表 `categories` | 经 `normalize_category` 归一 |
| `aov_n` | 推导 | `GMV ÷ 成交件数` |
| `gpm_proxy_n` | 推导 | `GMV ÷ (播放量 / 1000)`，列表近似值 |
| `video_gpm_n` / `live_gpm_n` / `avg_*_views_n` / `*_engagement_n` | 详情 | 列表阶段为空，由 L1 覆盖 |

### L1 安全预检查 → 剩余目标按达人复用详情

1. 规则启用了视频/直播组（`need_detail = rule.video_live.enabled`）；
2. 该行通过 `evaluate_custom_precheck`：没有列表确定失败、SKU 拦截/缺失或安全 blocks（包含非本次勾选商品）。

预筛与完整 evaluator 共用同一份判定：启用的粉丝、GMV、件数、女性占比、类目可先定失败；B005 SKU 使用 `evaluate_product_sku`（6PCS → failed，缺失 → needs_review）；主推/当前商品/关键 ID/不能批准仍保留原安全码。关键 ID 先转为不透明字符串，不转浮点。`can_be_approved=None` 不改成 False。

**详情可覆盖项不能提前淘汰**：视频/直播尚缺失，或 GPM / 客单价 / 履约率的列表值为空、不达标，均保留补详情机会。视频/直播组关闭时不延后这些指标、不强拉详情，仍完整执行原列表回退口径。预筛只减少请求，不删除任何申请或改变输出顺序；L2/L3 的最终判定与 L5 的完整复算不删除。

短路行的启用详情依赖项标 `needs_review`、`value=None`、`source=detail-uncollected`，说明「因基础条件/SKU/安全拦截已停止，本项未采集」，不是缺字段、不代表关闭或通过。已知列表/SKU failed 优先整体 failed；无失败而 SKU 缺失为 needs_review；blocked 独立保留。不设 `detail_error` 或 `detail_checked=True`，不使批次 integrity 不完整。`evaluate_custom_row(defer_detail=True)` 只供 preview 使用且自行复核预筛停止证据；默认 evaluator 和批准验证永远完整计算，不从行字段恢复该参数。`detail_skip_reason` 仅为诊断，不能授权批准。

详情字段经 `_overlay_detail_fields` 白名单深拷贝覆盖：`video_gpm`、`live_gpm`、`avg_video_views`、`avg_live_views`、`video_engagement`、`live_engagement`、`est_post_rate`、`overall_gpm`、`revenue_per_buyer`、`creator_type` 及对应 `*_n`。不覆盖申请 ID、商品、SKU、是否可批准或逐行 checks。

**本轮复用**：cache 局部于一次 preview，键为 `(store_id, creator_id)`。全快照内同 creator_id 必须有一致且非空的去首尾空白 `creator_name`；名字冲突/缺失则该 ID 不共享。名字只作防冲突信号，不能当已验证 handle；API 身份来自绑定 `creator_oec_id` 的请求。只缓存 `source_used=api` 且可信成功的白名单指标，缓存/覆盖均深拷贝；成功但缺指标仍可复用，规则如实失败。DOM 成功/失败、真实失败、系统错误和取消均不缓存，不新增 DOM 身份探测，不跨店/跨任务持久化。命中不请求、不等待、不改变熔断计数；熔断开启优先于缓存，不能用缓存恢复批次完整性。新鲜真实采集保留原 delay/timeout/retry。

**系统级故障熔断（与正式只读详情链共享）**：优先识别 API `business_code=100000`，兼容错误/回退原因中的 `code=100000` 或 `Please remove the plugin`，不把任意数字串或超时当系统错误。`auto` 首次命中就返回原 API 失败（`source_used=api`），不调用 DOM；第二、三次仍允许真实 API 采集确认。连续 3 次真实系统失败（`SYSTEMIC_DETAIL_FAILURE_LIMIT`）后，本轮剩余详情目标不再请求 API/DOM、不等待、不重试，标 `detail-api-systemic-failure`，按 `needs_review` 处理，只记一条批次汇总。真实成功、普通失败及普通异常中断连续性；跳过/缓存不增不清，取消直接传播，每次新任务创建局部状态。即使不一致结果为 `ok=true`，系统性 API 回退原因也不能被 DOM 成功掩盖。真实详情失败仍进入 `integrity_failures`，整批 `integrity_complete=false`、禁止执行；后来成功或复用不能恢复完整性。普通 API 失败仍可 auto DOM 回退；显式 dom/shadow 的读取、比较、权威 DOM 与原有外层失败计数保持不变。触发后人工检查插件/浏览器环境或等待平台恢复，不自动关插件或重开店。

**拉详情的唯一触发条件是「视频/直播组启用」**。因此若只想用详情口径的 GPM / 预计发布率，但仍希望不启用视频/直播组，当前实现不会拉详情——这两项会退回列表口径（见第 5 节）。

### L2 自定义规则三态判定

对每一行逐项 `triage`，四项结论：

| 情况 | 结论 |
|---|---|
| 启用的指标为 `None`（平台未返回 / 缺字段） | `failed`（不通过） |
| 启用的指标为 `None` 且该行详情采集失败（`detail_error`） | `needs_review`（批次 integrity 不完整，禁止执行） |
| 有值但不满足阈值 | `failed` |
| 有值且满足 | `passed` |
| 未启用 | `not_checked`（**不等于通过**） |
| 安全预筛已停止，启用详情依赖项未采集 | `needs_review`（未采集，不是网络故障；已知失败优先） |

基础条件 8 项，全部 AND，比较符第一版固定 `>`（客单价为区间）：

| 键 | 标签 | 取值字段 | 来源标注 |
|---|---|---|---|
| `followers` | 粉丝数 | `followers_n` | list |
| `gmv` | GMV | `gmv_n` | list |
| `units` | 成交件数 | `units_n` | list |
| `gpm` | 千次曝光成交/GPM | `overall_gpm_n` 优先，否则 `gpm_proxy_n` | `detail-official` / `list-proxy`（近似值会在证据里标注） |
| `aov` | 客单价 | `aov_detail_n` 优先，否则 `aov_n`（GMV ÷ 件数） | detail / derived |
| `fulfillment` | 履约率/预计发布率 | `est_post_rate_n` 优先，否则 `fulfillment_n` | `detail-est-post-rate` / `list-fulfillment` |
| `female_pct` | 女性粉丝占比 | `female_pct` | list |
| `categories` | 类目 | `categories_n` ∩ 白名单 | list；缺失或全不命中 → failed |

视频/直播组：

- 视频侧三指标（GPM / 均播 / 互动）全部参与；直播侧 GPM / 均播参与，互动可选；
- `either`：任一侧 `passed` 即组 passed；任一侧 `failed` 即 failed；两侧都未决（详情采集失败）→ needs_review；
- `both`：任一侧 failed 即 failed；两侧都 passed 才 passed；否则 needs_review；
- 组未启用 → `not_checked`。

**汇总**：任一启用项 failed → 整体 `failed`；否则任一 needs_review → 整体 `needs_review`；否则 `passed`。

**B005 固定检查（不在自定义开关中，不能关闭）：** `product_id=1732414717062320994` 时，额外生成 `b005_sku` 检查（`scripts/lib/auto_approval_sku.py`）。只读取本条申请的 `sku_desc`，包含 `6PCS`（不区分大小写）→ failed，空值/非字符串/占位符 → needs_review，确认不含 → passed，再与其他检查 AND。其他商品不增加此检查。SKU 缺失只使本行不可批准，不单独标记整批详情采集故障。

2026-09-17 ZClaw 实页核对：当前待审核行可从「N 条申请」旁箭头展开，展开容器为 `.core-table-expand-content`；显示 `SKU：` 的下一行与父行 React `record.apply_infos[]` 对应申请的 `sku_desc` 一致。实测一组包含三款商品，B005 子申请为 `6PCS（Full Color Value Pack）,L`，其余两款为 `L`。同源已登记列表接口 `agg_info[].apply_deatil.apply_info/apply_infos[].sku_desc` 也返回相同文本；无需为读取已有字段逐行点击展开。列表适配器已有 `sku_desc` 字段，DOM/API 两路均保留。商品标题里的 “6-Pack” 和数字 `sku_id` 都不能代替 SKU 文本。聚合 `apply_ids` 命中但非精确主申请时，预检不返回主申请的 SKU，防止把兄弟申请误当本条。

规则本身在预览前经 `validate_custom_rule`（`scripts/lib/auto_approval_rules.py:294`）严格校验：未知字段、非有限数字、超范围、非法组合（组未启用却启用单侧、both 未启用两侧、全部检查关闭）、非主推商品全部拒绝；`product_ids` 上限 20；内容窗口仅 7 天、`min_related` 仅 4。

### L3 安全拦截（blocked，非审核项）

| 拦截码 | 触发条件 |
|---|---|
| `not-hero` | `match_hero` 精确匹配主推货号 / 商品 ID 失败（禁止标题、描述、子串匹配） |
| `not-active-product` | 行商品不在本次规则的 `product_ids` 内 |
| `missing-apply-id` / `missing-creator-id` / `missing-product-id` | 关键 ID 缺失 |
| `cannot-approve` | `can_be_approved=false` |

`blocked` 与审核结论正交：审核项可能 passed 但被拦截，页面展示时**拦截优先**。

**唯一可批准标记**：

```text
custom_eligible = (custom_overall == "passed") && !blocked
```

### L4 内容审查（只对通过行付费）

目标行 = `custom_eligible && custom_overall == "passed"`（即 L2 + L3 都过）。failed / blocked 的行不进入内容审查，不产生视频采集与视觉调用。

- 规则 `content.enabled=true`：调用 `review_creator_rows`，窗口为最近 7×24 小时，要求 ≥4 条相关带货视频且其中 ≥1 条有展示证据；达人身份以视频作者与 `creator_name` 匹配为准，不接受导出里的 creator_id / sec_uid 当身份凭证。
- **七天边界启用 BLOCKED（2026-10-03 调查）**：供应商公开 OpenAPI 仅描述 `sort_type=0` 为最新，没有足够的跨页排序、置顶覆盖、游标时间上界与动态一致性保证，也未完成独立维护者审查。因此仍保守分页，可能读到原有 10 页/200 条上限；旧视频/整页旧/连续降序不能授权提前停止或 complete。合成乱序、边界、身份与限额回归已补齐；未新增可信停止原因、信任开关或 proof schema。证据及解锁条件见 [TikHub 视频分页窗口契约](./TikHub视频分页窗口契约.md)。
- **视觉候选调度（2026-10-03 修复）**：不足 4 条已确认相关视频只采集元数据；达到 4 条后，从已收集的第一条相关候选起按采集顺序审查（包括前三条），visual 写回对应视频的原 proof item，首次正面展示即停止 callback/分页。处理游标在调用前推进，单条失败只记白名单原因、消耗一次尝试并继续下一条，不在后续 callback 重试。已有候选审完且仍有额度才继续采集新候选。
- **全批成本与证据边界不变**：默认所有达人共享最多 5 次视觉尝试、600 秒内容预算，每次调用前检查；失败和已验证视觉缓存命中也占一次尝试，缓存命中不重新取详情/下载/抽帧/请求模型。已有 ≥4 条相关时预算或时间耗尽立即停并保留 partial；不足 4 条即使视觉额度为 0 也继续计数（仍受原 deadline/页数/条数上限约束），不改变 `require_display=false` 的计数路径。取消信号直接传播，不当成单视频失败。提早停止时相关数量仅是已知下界；稀疏画面无展示仍是 needs_review，HMAC、作者、七天窗口、24 小时新鲜度、模型/版本、帧哈希的独立校验不变。
- 规则 `content.enabled=false`：目标行不会被审核，写统一标记 `content_review_status=not_run` + `content_review_reason=custom_content_check_disabled`；执行边界只接受这个标记（见 L5）。
- 结果回写后重新定级：

| 内容结论 | 对行的影响 |
|---|---|
| `passed` | 保持 eligible |
| `failed` | `custom_overall = failed`、`custom_eligible = false` |
| `needs_review` | `custom_overall = needs_review`、`custom_eligible = false` |
| 审核过程抛异常 | 全部目标行 fail-closed 转 needs_review（`内容审核异常: ...`） |

- 若 `require_display=false`：完整性达标（`content_review_complete`）且相关数 ≥4，可将 needs_review 放宽为 passed，并在证据里标注 `display-evidence-not-required`。
- 关闭内容审查是合法状态，但执行边界要求「规则快照声明关闭」与「统一标记」同时成立，前端布尔量无法伪装。

### L5 执行边界复算（批准前）

两层防线，缺一不可。

**（1）服务端候选子集**（`create_execution`）

| 校验 | 失败 |
|---|---|
| 键入 `y` / `yes` 确认 | 400 `confirmation-required` |
| 幂等键非空且 ≤128 字符 | 400 `invalid-idempotency-key` |
| `apply_ids` 非空、无重复、数量 ≤ limit | 400 |
| limit 为正整数（默认 1，无上限） | 400 |
| 预览 `completed` + `integrity_complete` + 24 小时内新鲜 | 409 |
| 每个 `apply_id` ∈ 服务端 `custom_eligible=true` 候选 | 400 `candidate-not-eligible` |

**（2）脚本逐行复算**（`_run_execute`）

B005 额外边界：服务端要求候选保存的 `metrics.sku_desc` 与 `b005_sku` 通过证据一致，否则报 `b005-sku-evidence-invalid`；脚本 `verify_row_evidence` 同样重算该项并拒绝缺少证据的旧预览。状态预检后再检查即时读取的 SKU，含 `6PCS` 或缺失则 `skipped-b005-sku`，不调用批准接口、不写飞书。前端对缺少该证据的旧结果提示重新筛查。SKU 与证据随预览保存，不改变正式 SOP 的 0/1/2/3 入口。

| 顺序 | 校验 | 失败动作 |
|---|---|---|
| 1 | 规则重载 + `verify_preview_envelope`：schema / mode=custom / store / **rule hash** / 完整性 / 新鲜度 | 退出码 2，整批不执行 |
| 2 | apply_ids 文件与预览行匹配、数量 ≤ limit | 退出码 2 |
| 3 | `verify_row_evidence`：用规则**重算** L2 + L3，结论与逐项数量必须与预览一致；内容启用时重验证据，关闭时只接受统一标记 | 该行 `skipped-evidence-invalid` |
| 4 | 精确主推复核 `_reject_if_not_exact_hero` | `skipped-not-hero` |
| 5 | 货号解析 `resolve_sample_product_for_row` | `skipped-product-unresolved` |
| 6 | （写表开启时）飞书查重 `resolve_duplicate_record` 必须 `no-match` | `skipped-deduplicate-*` / `skipped-dedupe-error` |
| 7 | 只读状态预检 `check_pending_application_api` 必须 `pending-approvable` | `skipped-api-preflight-error` / `skipped-api-preflight-state` |
| 8 | 窄 API `approve_application_api`（`--write-source api` 固定） | 见下 |

批准结果判定（`decide_api_approval_outcome`）：

- 写接口接受（`success_count=1` 口径）→ `approved`，不等列表刷「待发货」（约 10 分钟延迟）；
- 写失败且复查仍在待审核 → `failed`；
- 身份不一致 / 超时 / 其他写结果不确定 → `unknown`。

`failed` 或 `unknown` 都会**停止本轮剩余行**（`stop_round`），不自动重试。批准成功后才写飞书（写表可关）；飞书写入结果不确定时记 `write-uncertain`，同样不自动重试。走完飞书写入的行之间间隔 1.5s（`EXECUTE_DELAY_SECONDS`）。

**产物与恢复**：执行结束后把预览行与执行结果合并写成 `<backup_prefix>_pre_execute.json`（及导出三件套），作为核对（reconcile）的唯一输入；服务端要求该文件存在才允许创建核对任务。reconcile 只做「平台确认转入待发货 / 飞书补写 / 订单号回填」，与执行共享同一个 limit 预算，**不重新批准**。

## 4. 页面如何呈现这些结论

页面不参与判定，只做展示与选择（`frontend/src/components/ResultsPanel.tsx`）：

- 单行分类优先级：`blocked` > `eligible` > `overall`（`passed` / `failed` / `needs_review`），默认停在 eligible tab；五个 tab 与顶部 stats 使用同一分类，切换后行数必须与对应徽标一致；
- 结果表首列为序号（按当前 tab 的筛选结果连续编号，分页后继续累加），底部为 Astryx `Pagination`（默认 20 条/页，可切 50/100；行数不超过每页条数时不显示）；
- 规则表单不提供「类目」开关：类目恒为启用、固定全部白名单类目（`normalizeRule` 强制），与正式 SOP 的类目条件一致；
- 「结果已失效」提示由前端语义比较判定（`rulesEqual`）：只比较启用状态与启用项取值，忽略 JSON 键序、类目顺序与整/浮点写法差异；此外，旧结果缺少 B005 SKU 检查证据时也提示重新筛查；
- 服务端持久化**全部**候选行（含 failed / blocked），带逐项 checks、safety_blocks、指标快照与内容证据路径，便于页面展示证据；
- 只有 eligible 行可被选择；选择结果仍会在 L5 被服务端与脚本各验一次。

## 5. 指标口径与数据源

| 指标 | 取值 | 备注 |
|---|---|---|
| 粉丝 / 件数 / 女性占比 / 类目 | 列表 | 无详情替代口径 |
| GMV | 列表 | — |
| 客单价 | 详情 `aov_detail_n` 优先，否则 `aov_n` = GMV ÷ 件数 | 与正式 SOP 一致；详情值需要 L1 拉详情 |
| GPM | 详情 `overall_gpm` 优先，否则列表近似 | 列表近似在证据里标 `list-proxy`，页面摘要也会写明 |

## 6. 统计与预览信封

预览信封（`auto_approval_preview`）包含 `rule` + `rule_hash` + `allowed_product_ids` + `integrity_complete` + `stats` + 逐行证据，写入 `exports/auto_approval/preview_<preview_id>.json`。

`stats` 计数口径：

| 桶 | 计数条件 |
|---|---|
| `blocked` | 有 safety_blocks（优先级最高，含审核结论为 passed 的行） |
| `eligible` / `passed` | `custom_eligible=true`（两个桶同步 +1） |
| `failed` | 审核或内容结论 failed |
| `needs_review` | 详情采集失败导致缺失、内容证据不足或内容审查未决 |

即 **`stats.passed` 恒等于 `stats.eligible`**：页面说的「通过」是完整漏斗后的可批准数，不是 L2 的通过数。

### 6.1 阶段耗时日志契约

`scripts/lib/screening_perf.py` 提供标准库运行域记录器。性能日志只增加到现有 logging 流，**不进入信封、custom_checks、缓存或签名证据**，不修改全局 formatter；没有运行上下文的底层计时调用不输出、不累计。自定义 preview 使用服务器 `preview_id` 作为 `run_id`；独立 `review_creator_rows` 使用临时随机 ID，有 preview 上下文时复用，不创建第二轮计数器。嵌套独立运行与顺序运行退出时均复位 ContextVar。

每行格式为 `[筛查耗时]` 紧接单行 JSON。顶层字段仅有：

- `event`：`begin` / `end`，每次进入阶段打印 begin，finally 打印 end；不逐次轮询打印。
- `run_id`：本轮关联 ID，不包含店铺、达人或网络地址。
- `stage`：登记的有限阶段名。
- `elapsed_ms`：单调时钟测量的毫秒，begin 为 0；不读取或改变业务 deadline。
- `status`：`success` / `error` / `skipped`，指处理状态，**不是行资格**。preview 成功导出但有待复核行时，`preview_total` 仍可为 success，详情/内容失败看对应子阶段与业务 integrity。
- `counts`：白名单非负整数计数。`reason_<有限原因码>` 也位于这里，不输出原始异常；未知原因统一 `unexpected_error`。原因计数是阶段诊断出现次数，同一个异常可能影响多个嵌套阶段，不能把原因合计当成独立失败请求数。
- `sequence`：运行内从 1 递增的日志序号，begin/end 均递增；不是达人或视频 ID。

**时间范围**：`preview_total` 从 `_run_preview` 进入到导出/汇总结束，含规则文件读取、导航、主推表、数值抽取、各阶段及导出，不含任务排队、进程启动或最终「预览已写入」一行。`navigation`、`hero_load` 单列；`list_scan` 包括列表 auto 的 API/DOM 回退；`detail_enrichment` 包括整段详情循环及主动等待，`rule_evaluation` 是逐行规则计算，`content_review` 包括配置读取、证据检查/保存和内容采集。**父阶段包含子阶段，不得把二者相加当作总耗时**。总计数读取 `preview_total` 的 end；独立内容运行读 `content_review` 的 end；这些汇总包含本轮子阶段计数并显式补 0，其余 end 是当前阶段直接累计的计数，缺少某项表示 0，不能再与汇总相加。

**详情计数单位与测量点**：

- `list_rows`、`detail_target_rows`、`rule_rows` 是申请行数；`detail_collections` 是预览真正调用详情编排的行次数，非成功数、非唯一达人。
- `detail_context_calls` 是实际获取页面上下文次数（已有 context 不再取）；`detail_profile_calls` 是逻辑 `request_json` 调用次数，`profile_type_2/3/4/5` 是各类型的调用次数。`detail_profile` 包括该调用和响应结构/业务码校验；不合并四种请求，**不代表 HTTP 尝试数**（内部重试未观测）。
- `detail_api_calls/success/failure` 是 API 适配器逻辑调用与结果数；`detail_dom_calls/success/failure` 是实际 DOM 详情读取调用与结果数。返回 `ok=false` 或抛异常都算失败；DOM 的原因计数为 `reason_direct_dom`、`reason_api_fallback`、`reason_shadow_dom`，不输出错误正文。
- `detail_target_rows` 是安全预筛后剩余详情目标申请数（包括可能命中的复用行）。
- `detail_delay_calls` 是新鲜成功采集后的主动 sleep 次数，缓存命中/预筛早退/熔断跳过不等待；`detail_delay` 测量实际等待，与网络计时分开。
- `detail_cache_hit` 是本轮成功 API 详情复用行数，`detail_prefilter_skipped` 是本次勾选商品中安全预筛停止的申请行数；不包含未勾选商品。`detail_circuit_skipped` 是预筛后目标中熔断跳过的行数。两种 skipped 互不混算；前者不设 detail_error，后者保持系统故障标记，不与内容 `creator_reuse` 混算。固定 8 个勾选商品申请的离线样本为 5 次预筛停止、3 个详情目标、2 次真实采集/等待、1 次缓存命中；候选与同源完整采集参考相同，不承诺实店耗时等比例下降。
  正式只读详情循环建立独立临时 `run_id`（已有运行上下文则复用），结束/异常/取消后复位；其 `detail_enrichment` 汇总仅覆盖本段详情，不能称整轮筛查。`reason_systemic_api_error` 是固定系统故障原因码，性能日志不携带远端原文。两条链的 10 行连续故障离线样本均为 `detail_api_failure=3`、`detail_dom_calls=0`、`detail_circuit_skipped=7`。

**内容计数单位与测量点**：

- `content_target_rows` 是进入内容库且销售通过的申请行数；`creator_collections` 是实际开始 collect 的达人次数，`creator_reuse` 是同批复用行数，`proof_reuse` 是输入行携带的完整、有效证据复用次数。复用不是新的采集。
- `video_page_calls/success/failure` 是 collect 中列表 fetch 的逻辑调用/成功/失败次数。`video_page_fetch` **只包 fetch**，不包遍历视频、回调下载/模型或整次 collect。`video_returned` 是返回条目数（含重复），`video_in_window/outside_window` 按整数时间分类返回条目，未知时间不归两桶；列表结构/数量非法时不遍历统计窗口，后续身份和元数据校验仍独立执行，不能把返回条目当成独立、已验证视频总数。结束原因计数为 `reason_complete/stopped/video_limit/pagination_stalled/page_limit`；page_limit 对应原业务 `pagination_limit`，stopped 是回调请求停止，不声称必然已通过。
- `video_detail_calls` 是视频详情 fetch 次数，不与列表分页混算。
- `media_download_attempts` 是每个媒体候选 URL 的实际 bounded_request 尝试次数，`media_download_bytes` 是成功返回字节数；失败候选也记录 error/end，不输出 URL。
- `frame_extract` 包整个 `_extract_frames`；`ffmpeg_calls` 是实际 `_run_ffmpeg` 调用次数（含首帧回退），`frames` 是成功抽出的帧数。FFmpeg 参数与 deadline 不变。
- `visual_cache_hit/miss` 是视觉缓存查询次数；`visual_attempts` 是原预算扣减后的视觉尝试数，可能失败于媒体/抽帧，也可能命中视觉缓存；`vision_model_calls` 只在实际调用 `_analyse_frames` 时累计。视觉缓存命中不产生下载、FFmpeg 或模型调用。`vision_model` 测量分析函数，不声称等于底层 HTTP 请求数。

`skipped` 常见原因是 disabled / no_targets；空列表仍按原逻辑返回失败（no_rows），不是成功筛出 0 人。采集错误只允许登记的安全原因码；新增性能日志不得含 API key、Authorization、签名媒体 URL、handle、sec_uid、prompt、模型原文、帧或 base64。原有业务/httpx 日志不在本项脱敏变更范围内，仍须敏感保管。

测量覆盖自定义 preview 与独立内容库；正式脚本仅覆盖只读详情循环，不能声称已覆盖整条正式链路。离线假时钟及合成输入校验计数、请求顺序、行资格和证据，不构成实店耗时基线或固定加速倍率承诺。

## 7. 不变量（改动不得破坏）

1. 关闭的检查是 `not_checked`，任何情况下不得当作通过。
2. 正常采集后启用销售指标缺失必须落到 `failed`；详情采集失败可落 `needs_review`，且该批次不得执行。安全预筛停止而未采集的详情项、B005 SKU 缺失均落 `needs_review`，不单独破坏批次完整性，本行不得执行。
3. 自定义规则只绑定本次任务快照；不写回 `filters.Criteria`，不改正式 SOP 行为。
4. 执行只接受「服务端生成的预览 + hash 一致 + 24 小时内 + 完整性通过」；规则一改，旧预览立即失效。
5. 批准集合必须 ⊆ 服务端 `custom_eligible` 候选，且逐行经脚本重算；页面布尔量不构成授权。
6. 内容审查启用时必须有合法证据；关闭时只接受统一 not_checked 标记。
7. 批准只走既有窄 API；批准成功后才写飞书；写结果不确定不写飞书、不自动重试。
8. 执行限量为正整数（默认 1，无上限），写任务运行中不可取消。

## 8. 自验与变更同步

离线验证入口（不触网、不做写操作）：

```bash
python -m pytest tests/test_auto_approval_rules.py tests/test_auto_approval_preview.py tests/assistant/test_auto_approval_service.py
```

出现以下改动时，**必须同步更新本文**：

- `evaluate_custom_row` / `validate_custom_rule` / `verify_row_evidence` / `verify_preview_envelope` 的判定与字段；
- 常量边界：`BASIC_LIMITS` / `VIDEO_LIVE_LIMITS` / `PRODUCT_IDS_MAX` / `PREVIEW_FRESHNESS_SECONDS` / `EXECUTE_LIMIT_DEFAULT` / `CONTENT_ALLOWED_DAYS` / `CONTENT_ALLOWED_MIN_RELATED` / `SYSTEMIC_DETAIL_FAILURE_LIMIT`；
- 拉详情的触发条件、内容审查窗口与展示证据要求；
- 执行链路的 preflight 顺序、批准结果判定（`decide_api_approval_outcome`）与备份/核对契约。
